# Physical Constraints

Source: consolidated project constraints maintained in this document and
`steps/shared/physical_constraints.py`.

These checks are mandatory gates for every generated design. The orchestrator
records a structured `physical_constraints.json` report for each candidate or
case. A design that fails an error-level physical constraint is recorded in the
history but is not eligible for simulation-backed ranking.

## Step 1 - Massing

Every massing candidate must check:

- Building height meets the input requirements.
- Building floor plan size meets the input requirements.
- Net floor area remains within the project tolerance used by the massing
  validator.
- The fixed central core stays inside every tier footprint.
- Every tier keeps at least `min_core_to_facade_depth_m` (4.5 m) of clear depth
  between the core and the facade, and the core occupies at most
  `max_core_area_share` (30%) of the tier's gross plate.
- An upper tier extends at most 1.5 m beyond the tier below, and at most one
  tier transition expands upward.

Implemented in:

- `steps/step1_massing_energy/stage1_massing_interface.py`
- `check_massing(...)`
- `steps/shared/physical_constraints.py` for shared stage constraint helpers

Reports are written to:

```text
%AUTOMATED_DESIGN_OUTPUT_ROOT%/step1_massing/llm_iterations/<candidate_id>/physical_constraints.json
```

## Step 2 - Envelope

Every envelope case must check:

- Building area meets the input requirements.
- Building height meets the input requirements.
- Building floor plan size meets the input requirements.
- Step 2 uses the active location baseline declared by
  `config/project_context.json` and `config/climate_profiles.json`.
- Overall WWR meets the input range, currently `0.50 <= WWR <= 0.90`.
- Every orientation-specific WWR value for `north`, `east`, `south`, and
  `west` meets the input range `0.50 <= WWR <= 0.90`.
- Thermal zones do not fail the generated-zone coverage audit.
- Thermal zones fully cover the conditioned area.
- Windows are located on exterior facade surfaces.
- Core boundary walls have no windows and are excluded from WWR.
- Shading devices are declared when a positive shading depth is requested.
- EnergyPlus reports zero severe/fatal geometry or envelope errors.

The current implementation uses the Stage 1 physical report, the Stage 2
candidate fields, the OpenStudio export log generated by
`replace_original_geometry.rb`, and EnergyPlus severe/fatal counts. Additional
OSM geometric collision auditing can be added later, but each case already
receives a pass/fail report with warnings when a deeper audit is not available.

Implemented in:

- `steps/shared/physical_constraints.py`
- `check_stage2_envelope(...)`
- `steps/step2_envelope/stage2_envelope_energyplus.py`

Reports are written to:

```text
%AUTOMATED_DESIGN_OUTPUT_ROOT%/step2_envelope_layout/physical_constraints/<case_id>.json
```

## Step 3 - HVAC

Step 3 uses the selected Step 2 `best_envelope.osm` as its baseline OSM. Every
HVAC case or LLM tool plan must check:

- HVAC system design is appropriate for the active location's climate.
- HVAC system type is appropriate for the building use and scale.
- HVAC design parameters comply with the active location's standards
  (`standards_priority` in `config/climate_profiles.json`) and ASHRAE design
  standards.
- Every conditioned zone is ventilated through a DOAS: a 100% outdoor-air
  loop serving every zone.
- In the simulation, each zone's mechanical outdoor air is below its
  occupants' requirement for at most 1% of occupied hours.
- Occupied PMV comfort is not more than one percentage point below the active
  same-location baseline.
- Autosized and hard-sized parameters are consistent.
- If autosizing is used, the autosized fields are explicitly declared.
- If capacities or operating values are manually specified, W/m2, L/s-m2,
  COP, fan pressure, pump head, water temperatures, and flow-related values
  are checked against reasonable ranges.
- Contradictory autosized and fixed values are not mixed.
- EnergyPlus reports zero severe/fatal HVAC errors.

Implemented in:

- `steps/shared/physical_constraints.py`
- `check_stage3_hvac(...)`
- `check_stage3_hvac_toolkit_bec(...)`
- `steps/step3_hvac/stage3_hvac_energyplus.py`
- `hvac_toolkit/schema.py`, which validates `autosized_fields` and
  `hard_sized_fields` for LLM tool plans.

Reports are written to:

```text
%AUTOMATED_DESIGN_OUTPUT_ROOT%/step3_hvac/physical_constraints/<case_id>.json
```
## Step 3 DOAS coil requirement

- Every Step 3 DOAS air loop must contain a cooling coil.
- Every DOAS air loop in all five locations must also contain a heating coil;
  in the mainland it is controlled to a fixed `20 C` leaving-air temperature.
- Hong Kong uses the same DOAS tools and coil topology, but the heating source
  and heating components must use an always-off availability schedule, with
  a placeholder controller at the cooling-coil leaving-air target.
- A case with a missing DOAS cooling or heating coil is invalid.
